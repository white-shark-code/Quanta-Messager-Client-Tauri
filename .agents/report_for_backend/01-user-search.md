# 01 — Поиск пользователей / batch-lookup профилей

**Приоритет:** 🟡 medium
**Статус:** обходим временным хаком на фронте (N+1 запросов)

---

## Проблема

Для отображения списка чатов и сообщений фронтенду нужны публичные PGP-ключи и базовая
информация о пользователях-собеседниках (UUID, email, fingerprint, дата регистрации).

Сейчас на бекенде есть только:

- `GET /users/me` — текущий пользователь
- `GET /users/{id}` (через `fastapi_users.get_users_router`) — пользователь по UUID

**Эндпоинтов нет:**
- ❌ Поиск по email / username
- ❌ Batch-lookup по списку UUID
- ❌ Получение публичного ключа другого пользователя (для шифрования ему сообщений)

## Что нужно

### 1. Batch-lookup пользователей (минимум для MVP)

```
GET /users/batch?ids=<uuid1>,<uuid2>,...
Authorization: Bearer <token>

Response: 200 OK
[
  { "id": "uuid1", "email": "a@example.com", "public_key": "<armored>", "fingerprint": "ABCD..." },
  { "id": "uuid2", "email": "b@example.com", "public_key": "<armored>", "fingerprint": "EF01..." }
]
```

**Зачем:** на фронте список диалогов отдаёт только UUID второй стороны
(см. `schemas.DefaultDialogChat`). Чтобы отобразить имя/аватар/зашифровать сообщение,
фронт делает N запросов к `/users/{id}`. Это N+1 на каждый refresh.

### 2. Получение публичного ключа

Публичный ключ должен быть доступен **любому зарегистрированному пользователю** —
это фундамент E2E-шифрования. Текущий эндпоинт `/users/{id}` от `fastapi-users`
не отдаёт `public_key` (используется схема `UserRead` без него).

**Варианты:**
- Добавить поле `public_key` в `UserRead` schema (раскрытие email тоже нормально).
- Сделать отдельный эндпоинт `GET /users/{id}/public-key` — отдаёт только публичный ключ.

Предпочтительно — **отдельный эндпоинт**: меньше данных, можно кешировать агрессивно,
не зависит от `fastapi-users`.

```
GET /users/{id}/public-key

Response: 200 OK
{
  "user_id": "uuid",
  "public_key": "<armored>",   // может быть null если пользователь ещё не настроил ключ
  "fingerprint": "ABCD..."       // null если ключа нет
}
```

### 3. (Опционально, на будущее) Поиск по email

**Не нужно для MVP.** Фронт планирует инвайты по UUID (как сейчас), что безопаснее.

Если когда-нибудь захотите добавить — это будет `GET /users/by-email/{email}` с rate-limit
и маскированием (не раскрывать, существует ли email).

## Как обходим сейчас (MVP)

- На каждый чат фронт кеширует `{ peerUserId → publicKey }` в Zustand.
- При первом контакте делает `GET /users/{peerUserId}` через `fastapi-users` (без ключа),
  затем отдельный запрос «дай ключ» — **но его тоже нет**, поэтому пока сохраняем UUID
  и просим пользователя попросить собеседника отправить первый зашифрованный message
  (тогда расшифровываем и кешируем его public_key из подписи).
- Это UX-проблема: первый чат начинается с «привет, пришли мне что-нибудь зашифрованное».

## Решение, которое мы просим

Минимум (для разблокировки нормального UX):
1. `GET /users/{id}/public-key` — отдаёт публичный ключ.
2. `GET /users/batch?ids=...` — для списков.

Опционально (когда захотите):
3. Поиск по email (с rate-limit и маскированием).
